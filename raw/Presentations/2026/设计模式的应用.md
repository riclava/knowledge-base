# 设计模式的应用

> 核心观点：设计模式不是为了让系统显得高级，而是在真实变化压力下，用可控的间接层换取局部稳定。

---

## 01. 设计模式的应用

### 页面内容

**从背类图到识别变化**

主讲人：曾宏

### 视觉建议

标题页保持极简。背景使用一段逐步演化的代码结构：条件分支、接口抽象、可替换实现。

### 讲述重点

这堂课不逐一背诵 23 个模式，而是讨论模式在什么时候出现、解决了哪种变化，以及它带来了什么新成本。

---

## 02. 记住 23 个名字，不等于会设计

### 页面内容

- 类图只能告诉你结构，不能告诉你为什么需要这个结构。
- 同一结构可能对应不同意图，同一意图也可能被不同语言特性实现。
- 真正需要掌握的是：变化来自哪里，应该被隔离到哪里。

**开场问题：**

> 如果说不出某个模式隔离了什么变化，它是不是多余的？

### 视觉建议

左侧展示密集的 23 个模式名称，右侧只保留一个问题：“什么会变？”

### 讲述重点

模式不是考试词汇，也不是简历标签。它是对反复出现的设计压力和解决结构的命名。

---

## 03. 几乎所有模式都在隔离变化

### 页面内容

~~~text
稳定的业务意图
      ↓
可控的抽象边界
      ↓
可以替换的变化实现
~~~

设计模式通常在做三件事：

- 找出最可能变化的维度。
- 让稳定部分只依赖一个抽象。
- 把变化限制在局部实现中。

### 视觉建议

使用“稳定核心—抽象边界—变化实现”的三层结构，多个实现从边界下方展开。

### 讲述重点

模式的统一判断标准不是 UML 是否相似，而是变化能否被限制在合理边界内。

---

## 04. 一个完整的模式决策必须回答五个问题

### 页面内容

1. **上下文**：问题发生在哪里？
2. **变化压力**：什么会频繁变化？
3. **约束**：哪些部分不能修改？
4. **结构**：引入什么边界和协作关系？
5. **代价**：新增了多少间接层和理解成本？

> 模式不是“答案名称”，而是一组带条件和代价的设计决策。

### 视觉建议

使用一条从上下文到代价的决策链，而不是五个独立卡片。

### 讲述重点

后续每个模式都按照这五个问题展开，避免只给定义和类图。

---

## 05. 三类模式对应三个工程问题

### 页面内容

| 分类 | 工程问题 | 数量 |
|---|---|---|
| 创建型 Creational | 对象如何被创建和装配？ | 5 |
| 结构型 Structural | 对象如何组合成更大的结构？ | 7 |
| 行为型 Behavioral | 对象如何协作、分配职责和流转状态？ | 11 |

**GoF 23 个模式：**

- 创建型：单例、工厂方法、抽象工厂、建造者、原型。
- 结构型：适配器、装饰器、代理、外观、组合、桥接、享元。
- 行为型：策略、观察者、模板方法、责任链、状态、命令、迭代器、中介者、备忘录、访问者、解释器。

### 视觉建议

以“创建—组合—协作”的三个连续问题组织模式全景，而不是平铺 23 个格子。

### 讲述重点

分类只是索引。真正选择模式时仍然从变化点和意图出发，而不是先选一个分类再套结构。

## 06. 组合与接口，是大多数模式生效的前提

### 页面内容

**优先组合而非继承：**

- 继承在编译期绑定结构。
- 组合允许在运行期装配和替换。
- 多个变化维度会让继承产生 M×N 的类数量。

**面向接口而非实现：**

- 稳定部分依赖能力契约。
- 具体实现可以独立演进。

### 视觉建议

对比一棵不断膨胀的继承树和一组通过接口组合的对象。

### 讲述重点

策略、装饰器、桥接等模式都在用组合避免继承爆炸；接口则提供可替换实现所需的稳定接缝。

---

## 07. 策略模式隔离“同一目标的不同算法”

### 页面内容

**变化压力：** 排序、计费、折扣、重试或传输算法需要替换。

~~~text
调用方 → Strategy 接口 → 算法 A / 算法 B / 算法 C
~~~

真实应用：

- Java `Comparator`：运行时注入比较策略。
- `RejectedExecutionHandler`：线程池拒绝策略。
- Go `sort.Slice` 的 `less` 函数。
- `http.Client` 的 `RoundTripper`。

### 视觉建议

一个稳定调用方连接多个可替换算法，并标出运行时选择。

### 讲述重点

策略不是“消灭所有 if/else”。只有当算法确实需要独立变化、替换或测试时，抽象策略才有价值。

---

## 08. 工厂隔离“创建哪个具体对象”的决策

### 页面内容

**变化压力：** 调用方知道需要某种能力，但不应该知道具体实现如何被选择和初始化。

~~~text
业务代码 → 工厂/注册表 → 具体实现
~~~

真实应用：

- JDBC `DriverManager.getConnection(url)` 根据 URL 选择数据库驱动。
- `Calendar.getInstance()` 返回适合当前环境的实现。
- 插件系统根据名称或配置创建实现。

### 视觉建议

业务代码只连接抽象产品；工厂在后方完成类型选择、依赖准备和实例返回。

### 讲述重点

工厂的价值不是把 `new` 换成另一个方法，而是把“选择具体类型”的决策从业务流程中抽走。

---

## 09. 建造者为复杂构造提供命名、顺序和校验

### 页面内容

**变化压力：** 构造参数多、可选项多、对象需要一次性校验或保持不可变。

~~~java
HttpRequest request = HttpRequest.newBuilder()
    .uri(uri)
    .header("Authorization", token)
    .timeout(Duration.ofSeconds(5))
    .build();
~~~

真实应用：

- Java `HttpRequest.Builder`。
- OkHttp `Request.Builder`。
- Protobuf Builder。
- Go 函数式选项。

### 视觉建议

从一条难以理解的长构造函数，演化到具名的分步构造过程。

### 讲述重点

建造者不是所有对象的默认写法。简单对象直接构造更清晰；复杂度达到参数爆炸、顺序约束或集中校验时才值得引入。

---

## 10. 单例经常是披着模式外衣的全局状态

### 页面内容

单例带来的便利：

- 全局唯一实例。
- 访问路径简单。
- 生命周期容易统一管理。

隐藏的代价：

- 依赖关系不可见。
- 测试难以替换。
- 共享可变状态造成隐式耦合。
- 初始化和并发语义复杂。

> 现代实践通常更适合让依赖注入容器管理“单实例生命周期”。

### 视觉建议

展示多个模块直接连向一个全局对象形成的隐式耦合，再对比显式构造函数注入。

### 讲述重点

Spring 的 `singleton` 是每个容器一个实例，不是每个 JVM 一个实例。需要区分生命周期管理和硬编码 GoF 单例。

---

## 11. 适配器用来偿还接口不兼容的历史债务

### 页面内容

**变化压力：** 客户端期待接口 A，但第三方或遗留组件只提供接口 B，而且不能直接修改。

~~~text
客户端 → 目标接口 → Adapter → 既有组件
~~~

真实应用：

- Java `InputStreamReader`：字节流适配为字符流。
- Spring MVC `HandlerAdapter`：统一不同 Controller 形态。
- Go `http.HandlerFunc`：普通函数适配为 `http.Handler`。
- 日志桥接：旧日志 API 适配到 SLF4J。

### 视觉建议

使用“插头—转接头—插座”的简单隐喻，再映射到两个真实接口。

### 讲述重点

适配器通常是事后解决既有不兼容问题。它应显式处理语义差异，而不是只机械转发方法名。

---

## 12. 装饰器让正交能力可以按需叠加

### 页面内容

**变化压力：** 缓冲、压缩、日志、鉴权、缓存等能力需要自由组合。

~~~java
new BufferedReader(
    new InputStreamReader(
        new FileInputStream(file)))
~~~

真实应用：

- Java IO 的流包装链。
- `Collections.synchronizedList()`、`unmodifiableList()`。
- Servlet Request/Response Wrapper。
- Go 和 Node.js 的 HTTP 中间件。

### 视觉建议

把一个基础对象逐层包裹，每一层只增加一种能力，并保持同一接口。

### 讲述重点

装饰器以更深调用链换取能力组合。包装顺序会改变行为，调试时必须能够还原实际生效的装饰链。

---

## 13. 代理关注的是“谁能访问、何时访问、如何访问”

### 页面内容

**变化压力：** 真实对象需要访问控制、懒加载、远程调用、缓存或横切逻辑。

~~~text
调用方 → Proxy → 真实对象或远程服务
~~~

真实应用：

- `java.lang.reflect.Proxy` 支撑 Spring AOP、MyBatis Mapper 等机制。
- Hibernate 懒加载代理。
- gRPC/Thrift 客户端 Stub。
- Go `httputil.ReverseProxy`。

### 视觉建议

代理位于调用方和真实对象之间，标出鉴权、缓存、远程传输或懒加载控制点。

### 讲述重点

代理与装饰器结构相近，但意图不同：装饰器增强能力，代理控制访问。代理的代价是行为可能不再“所见即所得”。

---

## 14. 外观模式用默认路径降低子系统认知成本

### 页面内容

**变化压力：** 使用一个复杂子系统需要了解过多对象、调用顺序和资源清理细节。

~~~text
调用方 → Facade → 多个子系统组件
~~~

真实应用：

- `JdbcTemplate` 封装连接、Statement、执行、结果处理和释放。
- SLF4J 为多种日志实现提供统一门面。
- 云厂商 SDK 封装签名、重试、序列化和网络调用。

### 视觉建议

调用方只面对一个简洁入口，外观后方展开多个仍可独立访问的子系统。

### 讲述重点

外观不等于隐藏所有底层能力，它提供的是一条低认知成本的默认路径。高级使用者仍然可以直接访问子系统。

---

## 15. 桥接模式解决两个独立变化维度的乘法爆炸

### 页面内容

假设存在两个变化维度：

~~~text
业务抽象：普通消息 / 加急消息
实现通道：邮件 / 短信 / App Push
~~~

继承可能产生 `2 × 3 = 6` 个子类；桥接把两个维度拆开，通过组合连接。

真实应用：

- JDBC 抽象接口与不同数据库驱动。
- 图形 API 与 OpenGL/Vulkan/软件渲染后端。
- 跨平台 UI 抽象与平台实现。

### 视觉建议

左侧展示 M×N 继承矩阵，右侧展示两个可以独立扩展的维度。

### 讲述重点

桥接要求提前识别两个真正独立的变化维度。维度判断错误时，它会变成没有收益的过度抽象。

---

## 16. 组合模式让叶子和容器可以被统一处理

### 页面内容

**变化压力：** 数据天然形成树结构，调用方需要统一操作单个节点和节点集合。

~~~text
Component
 ├─ Leaf
 └─ Composite
     ├─ Leaf
     └─ Composite
~~~

真实应用：

- 文件与目录。
- DOM 和 XML 文档树。
- React、Android、Swing 组件树。
- 组织架构和菜单树。

### 视觉建议

展示一棵同时包含叶子与容器节点的树，所有节点共享一个基础操作接口。

### 讲述重点

组合模式把递归结构转化为统一对象协议。需要谨慎决定容器专属操作是否应该出现在所有节点接口中。

---

## 17. 责任链把请求处理变成可插拔流水线

### 页面内容

**变化压力：** 请求需要经过鉴权、限流、日志、校验、业务处理等可调整步骤。

~~~text
请求 → 鉴权 → 限流 → 日志 → 业务处理 → 响应
~~~

真实应用：

- Servlet Filter 与 Spring Security 过滤器链。
- Netty `ChannelPipeline`。
- Go Web 中间件。
- Express `app.use(...)`。

### 视觉建议

使用一条横向请求链，明确每个节点都有“处理、继续或终止”的选择。

### 讲述重点

责任链提高了处理环节的可插拔性，但真实执行路径变得隐式。系统需要能够输出当前链顺序和每个环节的观测信息。

---

## 18. 观察者解耦发布者，却引入时间与生命周期问题

### 页面内容

**变化压力：** 一个状态变化需要通知数量不确定、持续变化的多个订阅者。

~~~text
Publisher → Observer A
          → Observer B
          → Observer C
~~~

真实应用：

- GUI 和浏览器事件监听。
- Spring `ApplicationEvent`。
- RxJava、Project Reactor、EventEmitter。
- 消息系统中的发布订阅思想。

需要额外设计：

- 同步还是异步？
- 顺序是否重要？
- 失败是否隔离？
- 何时退订？

### 视觉建议

发布者向多个订阅者扩散事件，在事件箭头上标出时序、失败和生命周期。

### 讲述重点

观察者降低了对象引用耦合，却可能增加时间耦合。Java 的 `Observable`/`Observer` 自 Java 9 起已废弃，不应作为现代实现推荐。

---

## 19. 状态模式让状态机取代散落的条件判断

### 页面内容

**变化压力：** 对象在不同状态下行为不同，状态转换规则不断增长。

~~~text
待支付 → 已支付 → 配送中 → 已完成
   └────────→ 已取消
~~~

状态模式的做法：

- 每个状态封装自己的合法行为。
- 状态转换显式化。
- Context 委托当前状态执行操作。

真实应用：订单、工单、游戏角色、协议状态机。

### 视觉建议

先展示散落在多个方法中的状态判断，再收敛为一张明确的状态转移图。

### 讲述重点

状态模式适合行为随状态明显变化的场景。状态很少、转移简单时，清晰的 `switch` 可能比多个状态类更容易维护。

---

## 20. 命令模式把“一次操作”变成可管理的数据

### 页面内容

**变化压力：** 操作需要排队、记录、重试、撤销、组合或延迟执行。

~~~text
调用者 → Command → Receiver
             ↓
       队列 / 日志 / 历史
~~~

真实应用：

- `Runnable`、`Callable` 与线程池任务队列。
- 编辑器 Undo/Redo。
- 消息队列中的命令消息。
- Celery、Sidekiq 等 Job。

### 视觉建议

把命令对象放入队列，分别进入执行器、日志和撤销历史。

### 讲述重点

当操作需要被保存、传输和调度时，它就不再只是一行函数调用，而成为一个有身份、有参数、有生命周期的对象。

---

## 21. 访问者用“稳定结构”换取“操作可扩展”

### 页面内容

**适用条件：** 元素类型稳定，但需要不断增加新的操作。

~~~text
稳定 AST 节点
   ×
类型检查 / 优化 / 代码生成 / 格式化
~~~

真实应用：

- 编译器遍历抽象语法树。
- Java `FileVisitor`、`ElementVisitor`。
- ASM `ClassVisitor`。
- 对 XML/JSON 树执行校验、导出和统计。

### 视觉建议

横向放稳定节点类型，纵向放持续增加的操作，突出访问者扩展的是操作维度。

### 讲述重点

访问者的代价是新增元素类型时必须修改所有访问者。结构不稳定时使用访问者，扩展成本会非常高。

---

## 22. 真实框架通常同时组合多种模式

### 页面内容

以一次 Web 请求为例：

~~~text
HTTP 请求
  ↓ HandlerAdapter：适配不同控制器
  ↓ Filter / Middleware：责任链与装饰器
  ↓ AOP Proxy：事务、权限、日志
  ↓ Strategy：序列化、路由、重试算法
  ↓ Facade：封装数据库或外部服务访问
  ↓
HTTP 响应
~~~

### 视觉建议

画一条真实请求路径，在每个阶段旁边标注模式名和它隔离的变化。

### 讲述重点

框架不会严格按教科书一次只用一个模式。多个模式可以组合，但每一层都必须有明确意图和边界。

## 23. 结构相似时，必须回到意图区分模式

### 页面内容

| 易混淆模式 | 关键区别 |
|---|---|
| 策略 vs 状态 | 外部选择算法 vs 内部驱动状态流转 |
| 装饰器 vs 代理 | 增强功能 vs 控制访问 |
| 工厂方法 vs 抽象工厂 | 创建单个产品 vs 创建一族配套产品 |
| 适配器 vs 外观 | 转换不兼容接口 vs 简化复杂子系统 |
| 适配器 vs 桥接 | 事后补救接口 vs 事前拆分两个变化维度 |
| 模板方法 vs 策略 | 继承定制步骤 vs 组合切换算法 |
| 建造者 vs 工厂 | 分步装配复杂对象 vs 一次返回对象 |

### 视觉建议

保持一张简洁对照表，重点突出每一对的“意图动词”。

### 讲述重点

面试或评审时，不要只说两个模式结构不同，要说明它们分别应对什么变化压力。

---

## 24. 语言能力越强，模式的类结构可能越轻

### 页面内容

传统 OO 结构在现代语言中的常见压缩：

| 模式意图 | 现代实现方式 |
|---|---|
| 策略 | 函数、Lambda、`std::function` |
| 命令 | 闭包、任务函数 |
| 观察者 | 回调、事件流、Channel |
| 迭代器 | 语言协议、生成器、Go `iter.Seq` |
| 工厂 | 注册表、泛型、反射、函数类型 |
| 建造者 | 具名参数、函数式选项 |

### 视觉建议

左侧展示传统多类结构，右侧展示函数、闭包或语言协议实现的紧凑版本。

### 讲述重点

模式表达的是设计意图，不要求保留 1990 年代 Java 风格的类数量。Go 1.23 的 `iter.Seq` 等能力就是模式随语言演进的例子。

## 25. 课堂练习：让模式从重构中自然出现

### 页面内容

**初始需求：** 订单完成后需要发送短信通知。

**后来变化：**

- 增加邮件和 App Push。
- 不同用户选择不同渠道。
- 通知失败需要重试。
- 需要记录审计日志。
- 部分渠道需要限流。

**讨论问题：**

1. 哪些是独立变化维度？
2. 哪些步骤属于稳定业务流程？
3. 策略、工厂、装饰器、责任链、观察者分别可能出现在哪里？
4. 哪些模式现在还不应该引入？

### 视觉建议

按需求出现顺序逐步增加变化压力，让学生每轮只做一次最小重构。

### 讲述重点

不要求得到唯一答案。评价标准是：变化是否被局部化、依赖是否可见、失败语义是否清楚，以及新增间接层是否值得。

---

## 26. 选择模式前，先回答这七个问题

### 页面内容

1. 真正会变化的是什么？
2. 变化是否已经发生，还是只存在于想象中？
3. 稳定部分应该依赖什么接口？
4. 组合能否替代继承？
5. 最简单的实现能否满足当前需求？
6. 新增的间接层如何测试、调试和观测？
7. 模式带来的收益是否大于理解成本？

> 说不出隔离了哪种变化的模式，就是负资产。

### 视觉建议

回到第 03 页的“稳定核心—抽象边界—变化实现”结构，用七个问题逐层复盘。

### 讲述重点

最终目标不是“使用更多模式”，而是让变化发生时，系统只需要在正确的位置发生最小改动。

## 内容准确性说明

- Spring 的 `singleton` 是每个容器一个实例，不是每个 JVM 一个实例。
- `java.util.Observable` / `Observer` 自 Java 9 起已废弃。
- Java `Object.clone()` 与 `super.clone()` 默认产生浅拷贝，不应被描述为通用深拷贝方案。
- Go 的 `iter.Seq` 与 range-over-func 需要 Go 1.23 或更高版本。
- 示例用于解释设计意图，省略了生产代码所需的错误处理、并发控制和资源释放。
