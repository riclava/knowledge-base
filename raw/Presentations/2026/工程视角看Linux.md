# 工程视角看 Linux

> 课程承诺：面对“系统很慢”“端口不通”这类模糊现象，学生能够说清楚问题，找到相关的 Linux 对象与系统层次，选择下一条有价值的证据，并通过复测判断修改是否有效。

## 课程定位

- **受众**：具备基础 Linux 命令经验，但缺少系统化排障经验的研究生或初级工程师。
- **时长**：60 分钟，包含课堂判断、案例讨论和迁移练习。
- **前置知识**：知道进程、文件、端口的基本概念；能够阅读简单命令输出。
- **课程主线**：一张运行时地图、一条证据驱动的调查闭环、一个贯穿案例、一个迁移问题。
- **不做什么**：不讲 Linux 命令大全，不平均铺开 CPU、内存、存储、网络的完整指标体系，也不展开容器、`epoll` 和监控平台架构。

## 学习结果

课程结束时，学生应该能够：

1. 把用户感受到的现象改写成带范围、时间和指标的问题描述。
2. 把应用行为映射到进程、文件描述符、系统调用和内核资源。
3. 区分用户症状、系统现象、工作假设和根因结论。
4. 说明下一条证据要验证什么，以及什么结果会推翻当前判断。
5. 用基线、单变量、同负载复测和回滚完成问题解决闭环。

## 教学设计

- **先判断，后揭晓**：关键页面先让学生选择下一步，再展示新证据。
- **同一案例贯穿**：从开场的服务变慢，一直追到责任进程、I/O 对象和复测结果。
- **命令服务于问题**：每个命令都必须回答一个明确问题，不展示脱离上下文的工具清单。
- **用迁移检验理解**：最后换成“端口不通”，检查学生能否复用同一调查方法。
- **案例数据边界**：性能案例均为教学用模拟数据，用于练习推理，不代表真实生产事故。

## 课程节奏

| 时间 | 页面 | 教学任务 |
|---|---:|---|
| 0–5 分钟 | 01–02 | 建立问题张力，记录学生的第一次判断 |
| 5–23 分钟 | 03–06 | 建立 Linux 运行时地图，理解进程和服务边界 |

## 02. CPU 只有 42%，服务为什么仍然很慢？

### 页面内容

~~~text
机器：8 核
接口 p95 延迟：80 ms → 900 ms
吞吐量：下降 35%
CPU user + system：42%
Load Average：15
~~~

**你准备先做什么？**

~~~text
重启服务？    增加资源？    查看日志？
执行 top？    检查网络？
~~~

> 先不要找标准答案：你选择这个动作，是想确认什么？

### 建议用时

4 分钟。

### 课堂动作

请学生选择一个动作并说明理由。保留两到三种不同答案，不判断对错。继续追问：

- 哪些数字直接说明用户真的感到变慢？
- CPU 只有 42%，能不能排除系统压力？
- 什么观察结果会让你改变刚才的判断？

### 视觉建议

先只出现五个指标和五种自然反应；追问逐条出现。不要在这一页展示方法论或答案。

### 讲述重点

学生需要先发现：重启、扩容、看日志和执行 `top` 都不是中性的动作，它们背后隐含着对问题位置和原因的判断。

## 03. 先跟一条请求走一遍 Linux

### 页面内容

~~~text
客户端请求
    ↓
Socket / 文件描述符
    ↓
应用进程或线程
    ↓
系统调用
    ↓
Linux 内核
    ↓
CPU / 内存 / 存储 / 网络
~~~

观察一个运行问题，只需要持续追问三个维度：

- **对象**：哪个进程、FD、Socket、文件或设备？
- **状态**：它正在运行、等待、排队，还是已经失败？
- **边界**：问题发生在应用、内核、资源还是外部依赖？

### 建议用时

5 分钟。

### 课堂动作

让学生把“接口变慢”放到路径最上方，然后问：从用户现象到硬件资源，中间哪些节点能够留下证据？

### 视觉建议

使用一条纵向请求路径。后续页面反复复用这张图，只高亮当前讨论的节点，不再创造新的总览图。

### 讲述重点

这张图不是 Linux 架构全景，而是一张调查导航图。命令的价值在于暴露某个节点的对象或状态。

## 04. 进程是排查运行问题的责任边界

### 页面内容

一个进程同时拥有：

- PID、父子关系与启动时间。
- 用户身份、工作目录和环境变量。
- 虚拟地址空间和资源统计。
- 文件描述符表与网络连接。
- 当前状态：运行、睡眠、不可中断等待或已退出待回收。

~~~bash
ps -eo pid,ppid,user,state,etime,comm
ls -l /proc/<PID>/fd
~~~

> 当系统出现异常，先找到“哪个进程正在做什么或等待什么”。

### 建议用时

4 分钟。

### 课堂动作

给出“CPU 高”“磁盘慢”“端口占用”三个现象，让学生回答最终是否都需要落到具体进程或服务。

### 视觉建议

中心放一个进程，周围只放身份、状态、FD、内存和父子关系五个观察面。避免展开完整 PCB 数据结构。

### 讲述重点

进程把运行现象和责任对象连接起来。这里不要求学生背进程状态码，只要求知道：状态描述的是进程此刻能否继续推进，以及它可能在等待什么。

## 05. FD 和系统调用把应用行为映射到内核对象

### 页面内容

- 文件描述符是进程访问文件、管道、终端和 Socket 的句柄。
- 系统调用是应用请求内核执行 I/O、网络、进程和内存操作的受控边界。
- 应用日志解释业务语义；FD 和系统调用解释进程正在操作什么、在哪里等待。

~~~bash
ls -l /proc/$$/fd
strace -c ls >/dev/null
~~~

~~~text
应用动作       Linux 证据
读取配置   →   openat() / read()
写入日志   →   write()
发起连接   →   socket() / connect()
创建任务   →   clone()
~~~

### 建议用时

4 分钟。

### 课堂动作

现场执行两个短命令。让学生先预测标准输出、标准错误和终端分别会对应哪些 FD，再观察结果。

### 视觉建议

左侧是应用动作，右侧是 FD 指向的对象和对应系统调用，中间只用一条边界线连接。

### 讲述重点

不要把 `strace` 讲成万能排障工具。它观察的是系统调用边界，适合在更高层证据不足时进一步缩小范围；真实生产环境还要考虑附加开销和观察范围。

## 06. 能启动的程序，还不是可管理的服务

### 页面内容

systemd 为进程补充运行契约：

- 以什么身份、目录和环境运行。
- 依赖什么，失败后是否重启。
- 日志、退出状态和启动失败如何被保留。
- CPU、内存、FD 等资源边界如何配置。

~~~text
SIGTERM
  ↓
停止接收新请求
  ↓
等待进行中任务
  ↓
刷新数据并关闭连接
  ↓
返回有意义的退出码
~~~

> 工程交付的不是“一个能启动的二进制”，而是一个可管理、可观察、可退出、可恢复的服务。

### 建议用时

5 分钟。

### 课堂动作

问学生：如果程序可以启动，但只能使用 root、日志写在临时目录、收到停止命令就丢请求，它是否已经可以交付？

### 视觉建议

把应用进程放在“服务契约”边界内，外围只标身份、启动、退出、日志和资源限制。不要画 systemd 的完整组件架构。

### 讲述重点

将权限、信号和 systemd 合并为服务生命周期问题。最小权限的意义是限制故障与攻击半径；优雅退出的意义是让部署、重启和故障恢复可控。

## 08. 性能恶化通常从排队和等待开始

### 页面内容

~~~text
负载增长
   ↓
某个资源逼近处理能力
   ↓
队列、等待或失速增加
   ↓
延迟上升、吞吐下降、错误增加
~~~

同一个“服务很慢”，等待可能发生在不同位置：

- 任务等待 CPU 调度。
- 进程等待存储 I/O 完成。
- 内存回收、换页或分配发生失速。
- 连接等待建连、重传、接收或外部依赖响应。

> 排障的关键不是先猜资源，而是寻找“工作卡在哪里”的证据。

### 建议用时

4 分钟。

### 课堂动作

把“增加 CPU”作为建议抛给学生，问：如果真正增加的是 I/O 等待，这个动作为什么可能没有效果？

### 视觉建议

使用一条因果链；在“等待”节点向外分出 CPU、存储、内存、网络四个短分支，不展开指标表。

### 讲述重点

这一页只建立统一模型，不分别讲四门性能专题。后续用存储 I/O 案例把模型走通。

## 09. Load 只能提示任务压力，不能告诉你根因

### 页面内容

- Linux Load Average 统计可运行任务和不可中断睡眠任务的数量变化。
- 它是 1、5、15 分钟窗口的衰减平均，不是百分比，也不会自动按 CPU 数归一化。
- 解读时必须结合 CPU 数、用户指标、进程状态和具体子系统证据。

| 联合现象 | 当前更值得验证的方向 |
|---|---|
| 高 Load + CPU 接近饱和 + 运行队列增长 | 计算或调度压力 |
| 高 Load + 多个长期 `D` 状态 + I/O 等待增长 | I/O 路径压力 |
| Load 短时升高，但延迟和错误稳定 | 短期波动，继续观察趋势 |

> “8 核机器，Load 为 15”不足以得出“CPU 已满”的结论。

### 建议用时

5 分钟。

### 课堂动作

先只展示“8 核、Load 15”，请学生投票 CPU 是否一定已经满载；再逐行揭示三组联合现象。

### 视觉建议

用三条小型对照时间线展示同样的高 Load 如何对应不同的 CPU、`R/D` 状态和用户延迟，不使用仪表盘式卡片。

### 讲述重点

Load 是调查入口，不是问题结论。让学生形成“单个指标不负责证明根因”的表达习惯。

## 10. 第一轮证据：哪些数字说明服务真的变慢？

### 页面内容

**课堂模拟数据｜14:00 开始出现异常**

~~~text
机器：8 核
接口 p95 延迟：80 ms → 900 ms
吞吐量：下降 35%
错误率：0.2% → 6.4%

CPU user + system：42%
Load Average：15
~~~

**请先回答：**

1. 哪些数字直接证明用户受到影响？
2. 哪些数字只是系统现象？
3. 下一步最值得区分的是哪几种等待？

### 建议用时

4 分钟。

### 课堂动作

让学生把指标分为“用户症状”和“系统现象”。要求回答中暂时不使用“根因是……”这类表达。

### 视觉建议

左侧展示用户指标，右侧展示 CPU 和 Load；先不使用颜色暗示答案。问题逐条出现。

### 讲述重点

延迟、吞吐和错误率定义了服务问题。CPU 和 Load 帮助选择调查方向，但它们还没有解释为什么变慢。

## 11. 第二轮证据：压力更像发生在存储路径

### 页面内容

**新增系统证据：**

~~~text
iowait：31%
vmstat 的 b 列持续升高
多个服务进程长时间处于 D 状态
磁盘 await 和队列长度同步升高
网卡错误和 TCP 重传没有明显变化
~~~

~~~text
当前可以说：
“存储 I/O 路径是最值得继续验证的方向。”

当前还不能说：
“磁盘就是唯一根因。”
~~~

**下一步问题：是谁在产生 I/O，正在访问什么？**

### 建议用时

5 分钟。

### 课堂动作

请学生指出哪几条证据互相加强，哪一条证据帮助暂时降低了网络方向的优先级。再让学生选择下一条进程级证据。

### 视觉建议

沿第 03 页的请求路径，高亮“进程 → 系统调用 → 存储”部分。系统证据逐条进入同一个工作假设，不画成互不相干的指标卡。

### 讲述重点

`iowait`、`D` 状态、`await` 和队列长度都不能单独证明根因；它们在同一时间窗口共同变化，才使存储路径成为更强的工作假设。

## 12. 第三轮证据：找到制造 I/O 压力的进程

### 页面内容

**新增进程与对象证据：**

~~~text
pidstat -d：backup-worker 持续大量顺序写入
/proc/2718/fd：输出指向 /data/backup/full.tar
任务启动时间：13:58
服务异常开始时间：14:00
应用数据与备份文件位于同一存储路径
~~~

**当前工作解释：**

~~~text
备份任务与在线服务竞争同一存储资源
→ I/O 队列和等待增加
→ 在线请求延迟与错误率恶化
~~~

**最小验证动作：**暂停备份任务，保持相同请求负载，再次观察用户指标和存储状态。

### 建议用时

4 分钟。

### 课堂动作

要求学生说明：为什么“启动时间接近”只能加强工作解释，仍然不能单独证明因果？暂停任务后需要同时观察哪些指标？

### 视觉建议

使用一条时间线连接备份启动、队列上升和服务恶化，再从备份进程连接到具体 FD 与存储路径。

### 讲述重点

调查从“磁盘可能有压力”收敛到了具体进程、具体对象和可验证的竞争关系。现在才具备设计最小实验的条件。

## 13. 暂停任务后变快，还要经过复测才能下结论

### 页面内容

**课堂模拟复测｜请求负载保持一致**

| 指标 | 备份运行 | 暂停备份 |
|---|---:|---:|
| 接口 p95 | 900 ms | 120 ms |
| 错误率 | 6.4% | 0.3% |
| 磁盘 await | 78 ms | 9 ms |
| 长时间 `D` 状态任务 | 14 | 0–1 |

~~~text
记录基线
→ 只改变一个变量
→ 在相同负载下复测
→ 检查改善与回归
→ 保留、调整或撤回
~~~

**可以形成的结论：**共享存储竞争已经成为解释本次性能恶化的强证据；下一步应评估错峰、I/O 限制或存储隔离，而不是直接套用通用调参清单。

### 建议用时

4 分钟。

### 课堂动作

先不展示结论，让学生判断哪些变化说明用户体验改善，哪些变化支持存储竞争解释。继续追问：如果暂停后用户指标没有改善，应该如何处理当前假设？

### 视觉建议

左侧为简洁的前后对照，右侧为单循环验证流程。在“保留/调整/撤回”处分叉。

### 讲述重点

服务恢复只是验证过程的一部分。工程上还需要确认相同负载、影响范围、回归风险和长期解决方案，并保留撤回路径。

## 14. 迁移题：端口不通时，先判断失败发生在哪一层

### 页面内容

**新场景：**

~~~text
curl http://server:8080/health
→ Connection refused

ping server：正常
ps：服务进程存在
~~~

**你准备先确认什么？**

~~~text
进程存在
≠ 服务已经监听
≠ 监听在正确地址
≠ 应用协议一定正常
~~~

**分层证据：**

1. `ss -lntp`：是否监听、监听在哪个地址？
2. `systemctl status` / 服务日志：启动和绑定是否成功？
3. `curl -v`：TCP 建连后，应用协议返回了什么？
4. 如果表现为超时，再检查路由、防火墙、丢包和链路。

### 动画揭晓

~~~text
ss -lntp
→ 127.0.0.1:8080

服务只监听本机回环地址，远程客户端无法访问。
~~~

### 建议用时

5 分钟。

### 课堂动作

由学生排列证据顺序，并说明每一步可能得到的不同结果。最后揭晓监听地址，再要求给出修改后的复测动作。

### 视觉建议

使用“客户端 → 网络 → 监听 Socket → 服务进程”的四段路径。先高亮失败点未知，揭晓后只高亮监听地址。

### 讲述重点

这道题不追求讲完整网络协议栈，而是检验学生是否会把模糊现象映射到对象、状态和边界。`ping` 正常不能证明 TCP 端口或应用协议正常；进程存在也不能证明服务已经正确监听。

## 15. 知道下一步该查什么，就是工程视角

### 页面内容

1. **问题是什么？** 对象、范围、时间和用户指标是否清楚？
2. **可能在哪一层？** 对应哪个进程、FD、Socket、文件或资源？
3. **需要什么证据？** 什么结果支持当前判断，什么结果会推翻它？
4. **最小安全动作是什么？** 能否只改变一个变量，并保留撤回路径？
5. **怎样证明真的改善？** 是否在相同负载下比较了用户指标和系统状态？

> AI 可以帮你查命令；你仍要决定该问什么、相信什么，以及修改有没有真的有效。

### 建议用时

2 分钟。

### 视觉建议

回到第 03 页的运行时地图，依次亮起问题、对象、证据、动作和复测五个节点。不要增加新的方法论图。

### 讲述重点

每亮起一个节点，就邀请学生回忆对应课堂动作。最后才点明：刚才从服务变慢到端口不通所反复进行的判断，就是“工程视角”。

## 准确性与教学边界

- “一切皆文件”是统一接口思想，不是“所有对象都是磁盘文件”；本课程不单独展开这一表述。
- Load Average 不等于 CPU 使用率，也不等于等待 CPU 的进程数量。
- 高 `iowait`、`D` 状态、`await` 或磁盘队列都不能单独证明根因。
- `Connection refused`、连接超时和应用协议错误应分别解释，不应都概括成“网络不通”。
- 生产环境使用 `strace` 等动态观察工具时，需要控制范围并评估附加开销。
- 性能优化必须以用户目标、基线和可重复复测为前提。
