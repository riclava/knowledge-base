## Core Thesis

- 设计模式是**面向对象设计中反复出现的问题的、经过验证的可复用解决方案模板**——不是能直接抄进项目的代码，而是"什么场景 / 什么结构 / 什么收益 / 什么代价"的经验总结。最经典来源是 GoF（Gang of Four）1994 年的《设计模式：可复用面向对象软件的基础》，归纳了 23 种模式。
- 它解决的核心问题是：**如何组织类与对象之间的关系，使系统面对变化时改动最小、复用最大、耦合最低。**
- 几乎所有模式的本质都在做同一件事——**把"会变的部分"和"不变的部分"分开，让变化被隔离在一个可控的边界里**。
- 模式的价值有两层：**工程价值**（久经考验的结构，避免重复踩坑）和**沟通价值**（模式名是团队通用词汇，说"这里用策略模式"比画半天类图更快）。

## GoF Classification

| 分类 | 关注点 | 一句话 | 数量 |
|---|---|---|---|
| 创建型（Creational） | 对象怎么被创建 | 把"创建"和"使用"解耦 | 5 |
| 结构型（Structural） | 类与对象怎么组合 | 把小结构拼成大结构，同时保持灵活 | 7 |
| 行为型（Behavioral） | 对象之间怎么协作、分配职责 | 把"算法/职责/交互"解耦 | 11 |

- 创建型：单例、工厂方法、抽象工厂、建造者、原型
- 结构型：适配器、装饰器、代理、外观、组合、桥接、享元
- 行为型：策略、观察者、模板方法、责任链、状态、命令、迭代器、中介者、备忘录、访问者、解释器

各模式的意图、要点与真实应用清单见 [[creational-patterns]]、[[structural-patterns]]、[[behavioral-patterns]]；跨类的总原则与易混淆对比见 [[design-patterns]]。

## Distinctive Contribution of This Source

相比常见的"模式定义 + UML"资料，这份笔记有三个明显取向：

1. **每个模式都带"真实应用"小节**，把模式锚定到 JDK、Spring、Netty、Servlet、JDBC、Go 标准库等具体实现上（例如 Java IO 的装饰器链、`Comparator` 的策略、`java.lang.reflect.Proxy` 支撑的 Spring AOP、`ChannelPipeline` 的责任链）。作者明确建议把这些小节当索引，带着模式意识去读源码。
2. **三语言并列实现（Go / Java / C++）**，顺带暴露语言差异：Go 用 `sync.Once`、函数类型工厂、函数式选项、`iter.Seq`；Java 用静态内部类 Holder、`Cloneable`、内部类备忘录；C++ 用 Meyers Singleton、`unique_ptr`、`std::function`、`rbegin/rend`。
3. **强调"认出意图比对照 UML 更重要"**，因为真实框架里少有教科书标准形态，模式常被裁剪、组合，或用函数、闭包、泛型、反射改写。

## Key Details / Pitfalls (from source)

- **模式是手段不是目的**：为了用模式而用模式是新手最常见的坑，会凭空增加间接层、抽象和类数量（over-engineering）。**先有真实的变化压力，再引入对应模式。**
- **优先组合而非继承**：GoF 两大总原则之一。继承是编译期强耦合，组合是运行期灵活装配；装饰器、策略、桥接都是"用组合替代继承爆炸"的典范。
- **面向接口编程，而非面向实现**：另一大总原则，是绝大多数模式起作用的前提。
- **易混淆的模式对**：策略 vs 状态（结构同、意图不同：外部选择 vs 内部流转）、装饰器 vs 代理（增强功能 vs 控制访问）、工厂方法 vs 抽象工厂（单产品多态创建 vs 一族产品搭配创建）、适配器 vs 外观（转换单个接口 vs 简化整个子系统）、适配器 vs 桥接（事后补救 vs 事前设计）。
- **单例的争议**：单例是全局状态，会隐藏依赖、破坏可测试性；多数场景更推荐用 DI 容器管理生命周期，而不是硬编码单例。来源还提醒 Spring 的 `singleton` 是"每容器一个"，不是 GoF 的"每 JVM 一个"。
- **模式会随语言演化**：在支持一等函数的语言里，策略、命令、观察者常直接用函数/闭包/委托实现，不必建一堆类；别把 Java 90 年代的写法照搬到现代语言。
- **具体模式的局部易错点**：单例的线程安全与全局状态、原型的深拷贝 vs 浅拷贝、享元要求内部状态不可变、观察者的同步通知/异常传播/忘记退订导致内存泄漏、备忘录快照体积、访问者"新增元素类型要改所有访问者"、解释器在文法复杂后类数量失控（应换 ANTLR / yacc 之类解析器生成器）。
- **注意已废弃 API**：`java.util.Observer` / `Observable` 自 Java 9 起已废弃，不应继续作为观察者模式示例推荐。

## Practice & Trade-offs (from source)

1. **从"识别变化点"入手，而不是从"套模式"入手**：先问"这段代码最可能因为什么原因而改？"，把那个变化维度隔离出去，往往自然落到某个模式上。
2. **重构中引入，而非一开始就设计满**：遵循三次法则 / AHA（Avoid Hasty Abstractions），等重复和变化模式看清楚了再用模式重构。
3. **权衡灵活性与复杂度**：每个模式都用"灵活性/解耦"换"更多的类和间接层"，只有变化确实会发生、收益大于理解成本时才划算。
4. **读源码时练习识别模式**："真实应用"小节可以当索引，比单纯背定义有效得多。
5. **和架构模式区分粒度**：本页是类/对象级设计模式；系统级模式（微服务、CQRS、Event Sourcing、六边形架构等）属于同一"设计"谱系上的不同粒度，见 H 模块其他条目。

## One-line Summary (from source)

设计模式就是一批"把会变的部分从不变的部分里隔离出去"的成熟套路——它的价值在隔离变化、降低耦合和统一沟通语言，但一定要在真实的变化压力下按需引入，为用而用只会平添复杂度。

## Documentation Implications

- 写模式类文档时，"意图 + 变化点 + 代价"比"结构图 + 角色名"更能帮助读者判断该不该用；本源的四段式（意图 → 要点 → 真实应用 → 实现）值得沿用为模板。
- 模式名是团队通用词汇，文档应使用规范中英文对照（如"责任链 Chain of Responsibility"），避免同一模式在不同页面出现多种译名。
- 涉及易混淆对（策略/状态、装饰器/代理、工厂方法/抽象工厂）时，应显式写出"结构相似但意图不同"，而不是只给结构图。
- 示例代码需要标注语言版本前提（Go 1.23 的 `iter.Seq`、C++11 起静态局部变量初始化线程安全、Java 9 起 `Observable` 废弃），否则会误导读者。
- 单例、`Observable` 这类有争议或已废弃的内容应保留"不推荐/已废弃"标注，而不是简单删掉——读者仍会在既有代码里遇到它们。
